# Case study: can the vCPU context layout be resolved at runtime?

`include/openhyp/ohv_hv_layouts.h` lists, per hv interface version, where each
block of the kernel-mapped vCPU context starts. This note explains how that
table is used today, whether the layout could instead be derived on the
running system, and what we recommend. No code was changed for it.

## Summary

| Question | Answer |
|---|---|
| Is the layout fixed at build time? | No. The row is chosen at runtime from the version word the kernel writes into the RO page (see "How a row is chosen"). |
| Is the `builds` column needed? | Not on any kernel in the table today: all four rows carry a non-zero `ver`, so the version-word match always wins and the build list is never consulted. |
| Can the layout be derived without the table? | Partly. The installed `Hypervisor.framework` carries the same offsets as load/store immediates, and `tools/offset_probe` already recovers most of them, but not all. |
| Recommendation | Keep the table as the primary source, use derivation as a fallback for unknown versions, and cross-check one against the other. Drop the `builds` column first. |

## What the table is for

OpenHypervisor talks to the kernel's hv traps directly. For every vCPU the
kernel maps two 16 KiB pages into the process:

- **RW page** — general registers, system registers, debug registers, vGIC
  state, run controls. The VMM writes it.
- **RO page** (at `+0x4000`) — version word, exit reason, ESR/FAR/HPFAR and
  state words. The kernel writes it.

The layout is a kernel structure and changes between versions. Blocks only
ever gain members at their end, but when a block in the middle grows,
everything after it moves: the run controls sit at `0x6a8` under 3.0.0 and at
`0x920` from 3.0.2, and 3.0.4 moved the state words, the extended registers
and the tail of the RO page again (`include/openhyp/ohv_context.h:238`).

The code is therefore split in two:

- **Shared by every layout** — member positions inside each block, the head
  of the RW page (x0/fp/lr/sp/pc/cpsr) and the head of the RO page
  (ver/exit_reason/...) are pinned with `static_assert` in `ohv_context.h`.
- **Version-dependent** — where each block starts comes from
  `ohv_hv_layouts.h` (`include/openhyp/ohv_context.h:244`).

The table is generated by lbr77/hv-layouts and holds offsets and sizes only.

## How a row is chosen

`ohv_layout_for` (`src/ohv_vcpu.cpp:3181`) and its caller in `hv_vcpu_create`
(`src/ohv_vcpu.cpp:3217-3238`):

1. After the first vCPU is created, read the version word at RO `+0x4000`,
   e.g. `0x2068797003000004`. The high 32 bits must equal
   `OHV_STATE_VER_MAGIC`, otherwise the vCPU is destroyed and `HV_ERROR` is
   returned; the low bits are the interface version, here 3.0.4.
2. Match the word exactly against the `ver` column.
3. Failing that, match `sysctl kern.osversion` against the `builds` column —
   a fallback for kernels that keep no version constant.
4. Failing both, print `refusing to guess at its context layout` and return
   `HV_UNSUPPORTED`.

The table has four rows, 3.0.0, 3.0.2, 3.0.3 and 3.0.4, all with a non-zero
`ver` (`include/openhyp/ohv_hv_layouts.h:66,112,158,204`). Step 2 always
matches on those kernels, so the build lists (`:69,115,161,207`) are not
reached; they only document which builds each layout was seen on.

## Deriving the layout from the installed framework

`Hypervisor.framework` ships with the kernel and is compiled against the same
structure layout, so the offsets appear as immediates in its `ldr`/`str`
instructions. The framework on disk always matches the running kernel.

`tools/offset_probe.cpp` works this way (`tools/offset_probe.cpp:6,224,290`):

- `dlopen` the installed framework, resolve exports such as
  `hv_vcpu_get_reg` with `dlsym`, and compute the slide.
- Exports are thin dispatchers, so follow `BL`/`B` edges depth-first, to a
  bound, into internal helpers and collect every load/store immediate met.
- Scan the whole of `__TEXT` for offsets referenced indirectly.
- Compare the findings against the pinned constants.

Result on a macOS 26A428 host (the probe only reads the framework; it creates
no VM):

```
44 checks: 25 direct match, 11 indirect, 0 drift, 8 missing
```

Everything it found agrees with the table — zero drift — but eight fields
were not found (among them those behind `amx_prepare` and
`monitor_data_abort`), so derivation alone cannot yet produce a full layout.

## Recommendation

1. **Keep the table as the primary path.** Debug information is the most
   authoritative source; keep matching on the exact version word.
2. **Drop the `builds` column.** Every row has a `ver`, so the column is
   unreachable. Before removing it, confirm no supported kernel lacks the
   version constant (the case the fallback was written for).
3. **Fall back to derivation for unknown versions.** Derive each block's
   start from the framework, then check it against two invariants — member
   positions inside a block do not change, and blocks keep their order — and
   use the result only if both hold; otherwise refuse as today. A new macOS
   release would then often run before the table is updated.
4. **Make the cross-check a test.** On every version the table covers,
   derivation must reproduce the table exactly.

Limits:

- Fields the framework itself never touches leave no immediate in its code
  and cannot be derived; the eight missing checks are of this kind.
- Derivation depends on the shape of compiler-generated code and can break
  if Apple's build changes. It is a fallback, not a replacement for the table.
